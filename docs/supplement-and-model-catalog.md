# 补充消息重生成与供应商模型目录

本次在现有回复缓冲、代次、提交锁、发送账本和 Provider 客户端上扩展。所有推理仍走 API；没有本地模型、独立发送器或新增自动模型轮换策略。

## 补充消息

首次触发开始固定计时。窗口内的私聊同会话补充直接关联；群聊参与者的补充交给轻量 API 判断，结果只允许引用宿主提供的消息 ID。群聊默认 500ms 合批、2s 判断超时；无关、不确定或失败的消息保留给下一轮。

确认补充后，在发送提交锁内使旧代次失效，再请求取消旧任务。等待短暂安静期后，把原始消息与相关补充按来源与时间重新送入既有 normal／YAML／Agent 管线。30 秒是允许替换的窗口，不是首轮固定等待时间。已开始发送、执行外部动作或结果未知时，不重跑这些动作；已确认的分段回复沿用协作打断合同。

| 配置字段（均以 `personification_` 开头） | 默认 | 含义 |
|---|---:|---|
| `supplement_enabled` | `true` | 启用安全补充合并 |
| `supplement_window_seconds` | `30` | 第一次触发起固定窗口 |
| `supplement_relation_batch_seconds` | `0.5` | 群聊关联判断合批时间 |
| `supplement_relation_timeout_seconds` | `2` | 每批关联判断时限 |
| `supplement_quiet_seconds` | `1` | 最后一条确认补充后的安静期 |
| `supplement_max_wait_seconds` | `3` | 一次补充合批等待上限 |

本地取消不保证远端停止生成或停止计费。`asyncio.Task.cancel()` 可以被被调协程捕获，所以旧代次还必须经过工具执行、模型结果、记忆状态提交及发送前的宿主校验。忽略取消的任务不占住下一轮的会话准入。

群聊关联判断保留候选消息的到达顺序；判断请求取消后，即使底层客户端继续运行，晚到结果也不会被接受。关联判断显式关闭支持该选项的调用器的工具与内置搜索。合批、安静期和最大等待允许配置为 `0`，不会被默认等待值覆盖。

## 多模型配置

WebUI 的 Provider 卡片保存一次连接信息，下面保存多个模型。每个模型有独立 `model_id`、显示名、能力声明、上下文容量和输入／输出限制。模型列表支持搜索、多选添加，也支持手动填写；发现模型列表不代表验证其工具或视觉能力。

连接字段按实际客户端能力显示。当前 OpenAI／CLI 路由支持供应商代理；Gemini、Anthropic 的既有客户端不读取该字段，界面会说明并保留已有值，不宣称代理已经生效。

`personification_model_purpose_bindings` 使用稳定供应商 ID 和模型 ID：

```json
{
  "main": {"provider_id": "gateway-a", "model_id": "large-model"},
  "lite": {"provider_id": "gateway-a", "model_id": "fast-model"},
  "vision": {"provider_id": "gateway-b", "model_id": "vision-model"}
}
```

支持 `main`、`lite`、`persona`、`compress`、`vision`、`labeler`。未设置的用途继承已有路由；严格主模型模式继续优先覆盖轻量判断／审核。未配置新绑定时，旧的角色覆盖和备用路由仍兼容。无效显式绑定不会静默匹配另一个供应商的同名模型。

保存后的配置供新回复使用；正在进行的补充重生成链保持首次输入时的配置快照。请求使用实际选中模型的预算，动态路由的工具结果仍由产生它的原客户端按原协议渲染。

视觉直连模型响应接入同一 Token 账本，按供应商路由和实际响应模型归属；即使该视觉结果因补充消息而作废，已经返回的有效用量仍保留计量。路由关闭上下文预算时尊重该配置。这里记录的是上游返回的用量，不代表已核对实际账单。

脱敏凭据按稳定供应商身份恢复，不依赖列表位置。删除正在被用途引用的模型必须先替换绑定或恢复继承；V2 批量保存支持在同一份请求里重新绑定并删除旧模型，联合校验通过后一次写入。

## 迁移和回滚

旧单模型条目兼容读为一个模型，不按相同地址自动合并供应商。第一次将旧池持久化为目录格式之前，在同一数据目录保留 `env.json.provider-catalog-v1.bak`，内容为原始配置字节，已有备份不覆盖。备份含凭据，应沿用配置文件的访问权限，不公开上传。

- 仅关闭补充行为：将 `personification_supplement_enabled` 设为 `false`，新轮恢复原排队行为。
- 恢复原用途路由：清空新用途绑定，保留现有默认模型、旧角色配置及备用路由。
- 完整源码回退：停止服务，备份当前配置，再还原部署前源码和对应配置；如恢复迁移备份，会同时恢复备份时的其他配置，须先核对后续修改。此次迁移不删除历史消息或记忆数据库。
- 启动前检查还原配置可读；启动后分别验证模型路由、只读动作、真实发送回执。源码测试通过不等于生产生效。

## 复用与验证依据

复用项目现有 `reply_buffer`、协作打断、发送提交锁、Provider 模型发现和请求客户端。取消机制依照 [Python asyncio 官方文档](https://docs.python.org/3/library/asyncio-task.html#task-cancellation)；无需引入额外消息队列或另一套 Agent 框架。官方取消说明直接支持“请求取消不保证任务已停止”，是否能阻止本插件晚到外发则由隔离测试验证。

测试使用合成消息、隔离存储和假 API，覆盖忽略取消、外部写入屏障、固定窗口、群关联失败、配置快照、默认模型切换、凭据重排和原子保存。真实 Provider 连通性、服务器部署和 QQ 外发需要分别验收，不能用模拟测试或模型列表发现代替。
